# Extension.BaGet.Identity.Application

The account and administration **use cases** of [BaGet Extension](https://pieroviano.github.io/BaGet/): business services (accounts, API keys,
ownership, administrators, rate limiters, email senders), the screen result and the screen gate. No MVC or Razor dependency (test-enforced);
the screens (controllers, views) are in [`Extension.BaGet.Identity`](https://www.nuget.org/packages/Extension.BaGet.Identity).

| Type | Role |
|---|---|
| `ScreenRef`, `ScreenCatalog` | A screen is its controller and default GET action (`AdminUsers/Index`); the catalog has one member per screen, used by `ScreenNext`, `ScreenLink` and `IScreenLinks` |
| `ScreenResult<T>` | What a use case returns for a screen: `Status` (Ok, Invalid, NotFound, Forbidden, SignIn, Next), `Model`, `Errors`, `Next`. The JSON UI API serialises it as it is |
| `ScreenGate` | Who may use a screen: accounts on, mail, signed in, administrator (or project administrator), access model present, server writable. View controllers and the JSON API both ask it |
| `SignInUseCase`, `RegistrationUseCase`, `ExternalSignInUseCase`, `AccountSettingsUseCase`, `TwoFactorUseCase`, `ApiKeysUseCase`, `AccountOverviewUseCase`, `ProfileUseCase` | The rules of the account screens (sign-in, two-factor steps, registration, mail round trips, settings, API keys, organizations, My packages/access, profile), registered by `AddBaGetAccounts`; the forms and screen models are in `Models/<area>` |
| `ScreenValidator`, `LocalUrls`, `AccountConfirmation`, `AccountLinks` | Form validation by DataAnnotations, the return-URL rule, the password/re-authentication confirmation, the absolute links of account emails (from `Site:PublicUrl` only) |
| `PackageManageUseCase`, `NpmManageUseCase`, `MavenManageUseCase`, `DockerManageUseCase`, `ContactOwnersUseCase`, `ValidationStatusUseCase`, `ScanArtifactUseCase` | The package-management screens (`Packages/*`): ownership, listing, deletion, scanning, validation status. Scoped; `EnterAsync` (owner / Delete-permission check, read-only mode) runs once per request. Their models (`PackageManageScreen`, `NpmManageViewModel`, ...) are the JSON of `/api/ui/packages/{id}/manage`, `/api/ui/npm-manage`, ... |
| `ExternalLogins`, `ExternalProviderMapping`, `SignInProviderSettings`, `OpenIdConnectProviderSetup` | The external OpenID Connect providers (`Services/Accounts`): which are configured / linked to a user, the per-provider administrator and group mapping applied at each sign-in through it, the Settings screen's *Sign-in providers* panel (named providers written to the overrides file), and the handler options per provider. The provider list itself is `OpenIdConnectProviderSet` (`BaGet.Core`), built at startup |
| `PackageScreenServices`, `IReauthenticationState` | What those use cases share (user, ownership, sensitive-action confirmation); the host implements `IReauthenticationState` over the sign-in cookie |
| `UiApiJson` | The JSON options of `/api/ui` (camelCase, enums by name, nulls left out) |
| `PasswordConfirmation`, `IScreenLinks` | The administrator's password (or recent provider sign-in) check and the "link to a screen" seam, so a use case never sees `HttpContext` or an URL helper (`IScreenLinks` is implemented by the screens project) |
| `Admin*UseCase` (`Users`, `UserDetail`, `UserDeletion`, `Packages`, `Organizations`, `Settings`, `Operations`, `Repositories`, `RepositoryEdit`, `RepositoryDelete`) | The use cases of the core administration screens (`Users`, `UserDetail`, `DeleteUser`, `UserPackages`, `Packages`, `Organizations`, `OrganizationDetail`, `Settings`, `Operations`, `Validation`, `Abuse`, `Cluster`, `Formats`, `AccessUnavailable`, and the repository screens `Repositories`, `RepositoryEdit`, `RepositoryDelete`: no answer carries an upstream password); registered by `AddBaGetAdminUseCases` while accounts are enabled |
| `AdminGroupsUseCase`, `AdminPermissionsUseCase`, `AdminProjectsUseCase`, `AdminAuditUseCase` (+ `AccessUseCaseBase`, `AccessCaller`, `AccessAuthorization`, `AccessPatternSupport`) | The access-control screens (`Groups`, `GroupDetail`, `Permissions`, `PermissionDetail`, `Projects`, `ProjectDetail`, `Audit`); the caller says whether it is a server administrator, the gate (not the use case) admits a project's administrators by the `name` route value through `AccessAuthorization`; forms in `Models/Access` |
| `RetentionUseCase`, `ScanningUseCase`, `ReplicationUseCase` | The retention (`Retention`, `RetentionPolicy`, `RetentionHolds`), vulnerability scanning (`Scanning`, `ScanRepository`, `ScanProject`) and replication (`Replication`, `ReplicationConfig`) screens, over `PolicyUseCaseBase` (password confirmation, `AccessModelException` shown on the screen the action returns to). Twins under `/api/ui/admin/retention`, `/scanning`, `/replication`; the peer API key of a replication and the scanner's registry credential are in no model |
| `Models/<area>/` | The DTOs of those screens (the JSON `model`) and the bodies of their writes, by area (`Account`, `Access`, `Admin`-side `Users`/`Organizations`/`Repositories`/`Settings`/`Operations`, `Packages`, `Policies`, `Shared`). A DTO never carries a password, hash, security stamp or API key value |
| `AccountAuthenticationService`, `ApiKeyService`, `PackageOwnershipService`, ... | The services `AddBaGetAccounts` registers while accounts are enabled; they are in `Services/Accounts`, `Services/Organizations` and `Services/Ownership` (namespace `BaGet.Identity.Application.Services.*`) |

`AddBaGetAccounts` (in `Extension.BaGet.Identity`) stays the entry point of a host; it calls `AddBaGetIdentityApplication` and, while accounts are enabled, `AddBaGetIdentityUseCases`.

## Layout

One type per file, no nested types, namespace = `BaGet.Identity.Application` + folder (`CodeLayoutTests`): `UseCases/{Account,Access,Admin,Packages,Policies}`, `Models/<area>`, `Services/{Accounts,Organizations,Ownership}`, `Screens` (result/gate types), `Security`, `Email`, `RateLimiting`, `Links`, `Extensions`.
